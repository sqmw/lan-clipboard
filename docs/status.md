# Status

## 当前定位

- 项目目标：同一局域网内，macOS / Windows 设备共享常用剪贴板内容
- 当前模型：相同 `shared_code` 的设备自动形成一个共享域
- 当前值模型：整个共享域共享一个“单槽位最新值”，谁最后复制，谁覆盖当前共享内容
- 当前同步方式：本地剪贴板指纹监听 + 队列调度 + TCP 二进制帧推送

## 当前已支持

### 平台

- macOS
- Windows

### 内容类型

- 纯文本：`text/plain`
- 图片：`image/png`
- 文件 / 目录：以 `tar` bundle 流式传输
- 富文本：`HTML` / `RTF`

### 发现与共享域

- `mDNS` 发现
- UDP 广播心跳
- 同共享码自动入域
- 多网卡环境手动选择本机使用网络
- 刷新时按当前选择网络即时过滤成员结果，不必先保存配置
- 切换网络下拉框后会自动触发一次共享域轻量刷新
- 未保存的网络草稿选择会在界面上保持，不会被后台状态轮询重置
- 不再支持手动填写兜底地址；共享域完全依赖自动发现

### 可靠性与体验

- 发送/接收双队列
- 新任务优先于旧重试
- 文本/富文本优先于图片，图片优先于文件
- 部分送达 / 剪贴板忙碌时自动短退避重试
- 若共享域当前只有本机，新的本地复制事件会直接丢弃，不再进入“暂无成员”的补重试
- 文件发送独立 bulk worker
- 文件发送按约 `16MB` raw payload frame 推进，文件体不再包进 `FileStreamChunk` 结构体
- 文件发送会边生成 `tar` bundle 边写入网络分帧，不再先落一个完整 outbound-cache 临时文件
- 文件接收完成后会把临时 archive 路径直接交给写回流程，不再把完整文件包读回内存
- 发送/接收进度展示
- 文本/富文本预览与展开
- 远端写回后的回环抑制
- 每次本地复制都会生成复制事件身份：`id`、`created_at_us`、`source_device_id` 与 `content_hash` 会随传输一起发送，用于判断“这是远端写回”还是“本机真的新复制”
- 富文本写回当前会同时保留原始 `HTML/RTF` 与一份纯文本兜底，减少“发送成功但某些目标应用粘贴无内容”的情况
- Windows 侧 `HTML` 读取当前直接读取 `CF_HTML` 原始字节，并按 `StartHTML/EndHTML` 偏移提取真实 `HTML`；不再把整段 `CF_HTML` 头和正文一起当普通字符串传输，避免中文乱码和 `Version:...StartHTML...` 这类头部泄漏到目标端
- 共享域上一次成功同步的内容指纹会作为当前共享槽位；下一次本地复制如果指纹相同，会在发送前直接拦截，不再重复广播
- 如果同一内容指纹已经在发送中，新的本地复制会被直接丢弃，避免同一个文件重复占用带宽
- 远端写回成功后，会把该内容哈希短时间登记到本机忽略表；监听线程如果再次读到同一内容，会直接丢弃，不允许再次转发
- 文件/目录回写后的判重改为轻量内容指纹（相对路径、类型、大小 + 部分文件内容采样哈希），不再因解包后的本地临时路径变化而被误判成新的本地复制，也不需要为判重完整读取整个文件
- 文件/目录远端写回会落在应用自己的临时接收目录；监听线程如果读到这些内部路径，会直接判定为远端写回并丢弃
- 本地监听入口对内部接收目录文件列表做最前置硬拦截；只要剪贴板里读到的是 `temp/lan-clipboard/...` 这类内部路径，就不会继续生成发送事件
- 接收远端内容期间，本地新的复制事件仍可被监听并按“新任务优先”进入流转
- 发送方中途下线时，接收端直接丢弃未完成文件流
- 新的复制事件会淘汰旧的排队任务；旧文件流若在传输途中被更新内容覆盖，也会被尽快终止/丢弃
- 发送目标会显式排除本机 `device_id` 和当前所选本机网络 IP，避免“自己复制自己接收”
- Windows 图片写入当前优先落盘为 `PNG + CF_DIB`，不再依赖之前不稳定的 `CF_BITMAP` 写入路径
- UI 支持语言切换（中文 / English），并可保存为默认显示语言

### 后台与启动

- macOS / Windows 启动后默认后台运行，不主动显示主窗口
- 主窗口当前不会在启动时创建；只有点托盘左键或菜单“打开窗口”时才会真正创建并显示
- “默认后台启动”当前不再依赖 `tauri.conf.json` 预创建主窗口；启动阶段只创建托盘，主窗口完全改为 Rust 侧按需创建
- 同步引擎和存在广播当前在 Rust `setup()` 后直接按本地设置启动，不再依赖主界面前端先跑起来
- Windows 后台启动时，存在广播线程会检查自身是否仍存活；如果 mDNS 注册因系统网络服务未就绪而失败，会在后台自动重试，不需要打开一次主窗口才能被其他设备发现
- 再次启动已有实例时会保持后台，不再通过单实例回调自动拉起主窗口
- 主窗口关闭按钮不会退出应用，只会隐藏窗口并保留菜单栏 / 系统托盘常驻
- 托盘 / 菜单栏交互统一为：左键打开主窗口，右键弹出菜单
- 当前菜单仅保留两项：`打开窗口`、`退出`
- macOS 菜单栏图标单独使用“双剪贴板共享”纯黑模板图标（由系统自动渲染成黑 / 白），不再复用应用主图标
- 支持“开机启动”开关，并持久化到设置
- `sync_status` 当前已收敛为纯状态读取，不再在前端轮询时隐式触发一次设备扫描
- “共享域成员数”和“设备列表”当前统一由设备列表刷新链路写入；`sync_status` 只更新运行状态，不再写成员数，避免主界面按钮刷新后又被状态轮询覆盖成旧值
- 前端设备刷新当前带有世代号保护；手动刷新开始前已发出的状态/缓存轮询结果，即使稍后返回，也不能覆盖本次按钮刷新的成员列表
- 前端状态/成员/传输刷新当前带有“运行中互斥 + 内容未变化不重绘”，Windows 拖动窗口时不再被高频空刷新打断
- 手动“刷新”当前在后台工作线程里执行设备发现，不再把主界面滚动和交互一起卡住
- 主动发现得到的 `mDNS` 结果当前只作为候选设备，写回共享域成员缓存前必须通过一次短 TCP 存活探测，避免 Windows 把已退出应用的陈旧 `mDNS` 记录重新显示成在线成员
- 手动“刷新”当前会在主动发现后额外等待约 `700ms`，把后台 `UDP` 心跳刚收到的成员一并合并回来，避免看起来像“必须等下一轮后台轮询才更新”
- 发送目标当前只以“当前可见共享域成员”计算；如果共享域里只剩本机，新的复制事件会直接丢弃，不再因为历史缓存地址继续发起发送
- 一旦新的发现结果确认共享域只剩本机，运行中的发送会被主动标记失败并尽快停止；活跃接收如果对应发送方已不在当前可见成员里，也会被标记停止
- `macOS` 当前不再用 `clipboard-master` 的系统回调监听复制事件，而改为后台线程轮询剪贴板哈希，避免复制时把已有主窗口重新拉到前台
- `Windows` 当前同样改为后台线程轮询剪贴板指纹，不再用系统回调监听，避免安装版在文件复制回调链路里触发进程退出
- 相同剪贴板内容在本地轮询监听下当前只会被视为同一条本地观察，不会因为轮询持续命中而反复生成新的发送任务
- `macOS` 启动轮询监听前会先建立本地剪贴板基线，避免应用刚启动时把系统里原本就存在的旧内容误当成一次新的复制并广播出去

## 当前不承诺

- 任意私有剪贴板格式的跨平台完全等价
- 应用私有对象 / 富媒体嵌入 / 自定义原生格式完整保真
- 历史记录持久化
- 托盘 / 开机自启 / 独立后台 daemon

## 当前已知边界

- “任何类型”当前实际承诺的是“跨平台支持的格式集合”，不是无限制全格式
- 超大图片会在发送前自动缩小到限制范围内
- 文件复制依赖本机源端能被正确识别为系统文件列表；如果源应用只提供路径文本，就会退化成文本同步
- Windows `RTF` 仍有兼容路径，后续还可以继续原生化
- 当前文件链路已改成独立 sender 线程 + raw payload frame + 发送端流水线打包 + 接收端路径型 archive 写回，避免发送方 UI 被文件网络发送卡住，并减少接收端大文件内存拷贝；但还没有承诺稳定拉满局域网带宽，后续若继续追求上限，需要继续做零拷贝、系统剪贴板交互和加密数据面的优化

## 当前关键参数

- 剪贴板监听间隔：自适应退避，变化后 `50ms`，空闲时指数退避到 `500ms`
- 远端写回本机后的内容忽略保留时间：`10000ms`
- 主同步循环空闲间隔：自适应（活跃约 `15ms`，空闲约 `80ms`）
- 后台自动发现间隔：`3000ms`
- 前端状态/成员刷新间隔：`1800ms`
- 前端传输进度刷新间隔：`500ms`
- 队列首轮退避：`30ms`
- 队列最大退避：`500ms`
- 文件流 raw payload frame：约 `16MB`
- 文件发送：文件打包与网络发送在独立 sender 线程执行，不阻塞 outbound 队列线程
- 发送端传输进度更新：后端约 `250ms` 一次，避免发送方 UI 被高频进度刷新拖慢
- TCP 收发缓冲：约 `16MB`
- `tauri dev` 调试构建会对加密与二进制编解码相关依赖启用 `opt-level=3`，避免 debug profile 把局域网吞吐误压到几 MB/s
- 文件体加密：`ChaCha20-Poly1305`
- 启用加密传输会明显降低大文件传输速度；如果只在可信局域网内使用且更看重吞吐，可以关闭加密
- UI 最大可配置发送大小：`1-1000 MB`
- 当前网络过滤粒度：按所选 IPv4 的前 `3` 段（`/24` 视角）筛选共享域成员
- Windows 多网卡场景：默认会尽量避开常见虚拟网卡（如 Hyper-V/WSL/Tailscale 等）来选择本机 IP；如仍不符合预期，请手动在“使用网络”里选择正确网卡
- 如果“使用网络”里保存的 IP 已不再存在于本机网卡列表（例如 DHCP 变更），应用会自动忽略该旧 IP 并回落到当前可用网卡

## 当前最值得继续优化的方向

1. 大文件实际吞吐与首包延迟
2. 图片链路在双端上的稳定性与一致性
3. 失败原因在 UI 上的细分展示
4. 后台常驻与系统集成体验

## 吞吐说明

- 当前版本已把文件流从 `FileStreamChunk` / `WireMessage` 大块封装改成专用 raw payload frame，并把发送端改为边打包边发送，减少协议包装、完整 tar 临时文件和磁盘二次读取；接收端也不再把完整 archive 二次读回内存
- 当前版本仍优先保证“能传、不断、可调试”，还没有把局域网传输吞吐优化到稳定吃满带宽
- 对小文本和常规剪贴板同步，当前体验重点是低延迟
- 对大图片、几十 MB 以上文件、连续大文件广播这类场景，当前速度不应被理解为最终形态
- 如果项目目标改成“尽量吃满带宽”，后续还需要继续优化：
  - 系统剪贴板写回路径和底层文件解包/落盘链路，减少大文件写回前后的额外等待
  - 文件分片、零拷贝与发送调度
  - socket / buffer / timeout 策略
  - 系统剪贴板读写与归档打包开销
